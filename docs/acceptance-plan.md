## 完成狀態與證據

每個項目依序使用「待開始 → 進行中 → 待驗收 → 完成」；依賴環境或使用者決策時
標「受阻」，記錄具體原因與解除條件。未執行、跳過、環境不可用都不算通過。

每個交付單元必須包含：原始碼或文件、必要的行為回歸測試、使用方式、驗證紀錄、
已知限制與交接更新。驗證紀錄須有日期、版本／差異、平台、命令、退出碼與結果摘要；
缺陷修正後重跑受影響檢查，不能沿用修正前的證據。測試數量只記錄結果，不是品質門檻。

若發現錯誤放行、無效命令送出、假成功、資料遺失、舊設定覆蓋新設定或可重現的
資源洩漏，該階段不得完成。其他警告須寫明影響、處置與追蹤項目，不得因測試綠燈隱藏。
測試不得被停用或放寬斷言來取得通過；也不得以減少安全限制替代修正。

### S1 必驗情境

使用臨時資料目錄、假 runtime／sink 及隔離服務埠；不得讀取本機實機設定來啟動 host。
瀏覽器測試須有真實 API 與檔案保存流程，不能全部以前端 mock 代替。

1. 建立／匯入計畫、編譯、儲存、重新載入；原有規則保留，同名新增不覆寫。
2. 未完成 JSON、原始宣告文字在重新整理後保留；損壞與滿額儲存有明確提示及可用重試。
3. 恢復草稿後不恢復可套用 token 或座標確認；編輯後舊編譯與預覽立即失效。
4. 座標框未確認、缺少 FK、退化幾何、非有限值、單位衝突阻擋套用。
5. 中英文量化規則可供審閱；任何未解析子句使整份請求無可加入元件。
6. hot reload 先 pending，只有週期 receipt 才 applied；重啟需求只顯示已存檔待重啟。
7. 預覽後修改設定／任務、停止／重啟、套用途中被取代、儲存失敗與 rollback，
   都保留真實結果，不覆蓋其他修改，不把歷史紀錄誤稱目前啟用。
8. A/B 逐週期比較、保存完整區間、重跑 PASS 與刻意失敗案例；缺資料、指紋變更、
   損壞案例與 filename／ID 不符回報錯誤。過期網路回應不覆蓋新的選擇。
9. Stackfile 編輯、錄製檔切換、Risk Log 篩選和隔離服務啟停的既有回歸保持通過；
   刪除與部分失敗僅使用可丟棄資料驗證，不接觸使用者錄製資料。

### S2 必驗契約

先盤點 SDK 與 runtime 的原始、修正、hold、retreat、emergency-stop 路徑，
列明位置／速度／夾爪／時間戳及 command-space 的允許型別、形狀、單位與缺值語意。
不能把「全零」當成所有命令種類的通用安全輸出。

對每個可送出路徑與 ENFORCE／MONITOR／LOG_ONLY 模式，注入 NaN、Infinity、
錯誤維度、無效選用欄位、缺少 fallback 必需觀測、guard／fallback／sink 例外。
驗收以 fake sink 實際收到的資料為準：

- 無效命令的 sink 呼叫數為零；觀測模式不豁免資料有效性檢查。
- fallback 失敗不退回原始不合法命令；停止／抑制輸出行為可辨識且不假裝成功。
- sink 拋錯不標為送出成功；cycle 結果保留故障來源與原因。
- 有效命令保留契約允許的欄位；正常 PASS／CLAMP 與 R01–R03 語意不回歸。
- 不以重跑 callback 造成同一週期重複副作用；SDK 與 runtime 對同樣資料的一致性有測試。

### L4 平台宣告門檻

先逐格盤點目前 Python 最低版本、分類器與 release workflow 的作業系統／架構，
將「可建出 wheel」和「已驗證執行」分欄。預定核心執行驗證至少涵蓋 macOS arm64
與 Linux x86_64 的 Python 3.11／3.12；其他版本、Linux arm64、Windows 等既有
產物目標須補驗或明確列為實驗性，不默默當成已支援。此表是驗證目標，並非目前保證。

CPU Tensor 必驗 dtype、requires-grad、bfloat16、溢位與輸出 device；CUDA／MPS
在相應環境驗證。沒有環境就保留受阻或不支援狀態，不能以 skip 補足支援宣告。
改變最低版本、支援平台或安裝契約需留下明確決策與使用者可見文件。

### L5 數值門檻與量測方式

以下是新設定的驗收目標，不是已達成的效能數字：

- 固定平台、依賴、配置、輸入大小及控制頻率；暖身後至少 10,000 cycles，報告
  p50／p95／p99、最大值與超期率。先記錄可重現基線，再凍結平台預算，不事後調寬。
- 標準離線 50 Hz 場景以 20 ms 為週期：快路徑與交接開銷 p99 不超過 10 ms，
  整輪超過 20 ms 比例不超過 0.1%；首次初始化和慢速首次等待另列，不隱藏在平均值。
  任一必需配置未達標，必須修正或明確限制支援頻率，不能宣稱硬即時保證。
- 至少 1,000 次建立／執行／reset／close，以及 8 小時固定負載 soak。
  每次完成清理後無遺留的 DAM worker；檔案描述符相對暖身基線沒有淨增加。
  soak 每小時採同條件樣本，末小時 RSS 中位數不高於暖身後首小時 10%，
  且無持續單調成長；不通過時定位保留物件，不能只提高門檻。
- callback 逾時、solver／錄製／儲存失敗均有可見錯誤；故障解除後依公開生命週期
  可回復；不存在無界重試、混用舊 verdict 或失敗後仍宣稱正常送出。

## 每階段交付與最終結案

每階段交付一份可獨立審閱的差異及驗收報告。報告逐條引用本文件編號，列出證據位置、
未完成條件、風險與下一步；已完成項目附對應 commit 或明確差異基準。未提交修改必須
標記，不能把乾淨 checkout 的測試結果套用到未知變更。發布與實機操作另依授權處理。

短期 S3 與最終候選版皆執行同版本的完整檢查：Python 非硬體測試、Rust 測試、
前端全套測試、正式建置、適用的 Ruff／format／mypy／pre-commit、docs-check；
再加上該階段所需的瀏覽器、乾淨安裝或長時間測試。成功訊息必須與退出碼一致。
已有警告須記錄是否影響安裝、建置或測試隔離，阻擋發布者須先修正。

**離線軟體範圍完成**：S1–S3、L1–L6 所有必需條件有同一候選版本的適用證據；
無未處理阻擋缺陷；支援矩陣與限制準確；範例可重現；交付版本、變更摘要與回復方式齊備。
若長期項目仍待辦，只能稱「短期交付完成」，不得宣布整體完成。

**特定設備部署完成**：另須指定 robot、task、action contract、校準、頻率與設備環境，
在明確授權與受監督條件下驗證停止、fallback、斷線與恢復，保留操作紀錄。
未指定設備時此門檻不納入離線軟體完成，但不得宣稱實機部署完成或安全認證。

執行順序固定為 S1 → S2 → S3 → L1 → L2 → L3 → L4 → L5 → L6 → 最終候選版驗收。
每個單元依「盤點差距 → 重現／驗證 → 修正 → 審閱 → 驗收 → 更新交接」推進；
失敗回到同一單元修正，不擴張到無關新功能。跨平台環境或實機授權受阻時，記錄解除條件，
繼續可獨立完成的工作，不把受阻項目標為完成。本計畫不會自動恢復已暫停的排程。
